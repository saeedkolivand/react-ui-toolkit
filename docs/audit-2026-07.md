## Open — found, not changed

### 1. Dark mode does not work

`README.md` advertises _"Dark Mode — Built-in dark mode support"_ and `tailwind.config.js` sets
`darkMode: "class"`, but `ThemeProvider` (`src/context/ThemeContext.tsx`) only holds a `useState`
value — **it never adds the `dark` class to the DOM**. So `ThemeToggle` flips a boolean that nothing
renders from, and every `dark:` utility in the components is dead.

The fix is roughly four lines (a `useEffect` toggling `document.documentElement.classList`, plus
`localStorage` and a `prefers-color-scheme` default), but it changes library behaviour rather than the
toolchain, so it was left for a deliberate decision.

### 2. React Compiler lint rules are warnings, not errors

`eslint-plugin-react-hooks` v7 adds ~14 React Compiler rules to the two that v4 enforced. Six fire on
real code:

| File                          | Rule                            |
| ----------------------------- | ------------------------------- |
| `Tooltip.tsx:92`              | `set-state-in-effect`           |
| `Tooltip.tsx:102` (×2)        | `refs` — ref read during render |
| `NotificationProvider.tsx:37` | `set-state-in-effect`           |
| `Tabs.tsx:63`                 | `set-state-in-effect`           |

Five are the standard portal-`mounted` and derived-state-sync patterns — discouraged by the compiler
rules but not defects. Reworking four components' lifecycles is a behaviour change, so the _new_ rules
sit at `"warn"` in `eslint.config.mjs` (prior strictness is unchanged: `rules-of-hooks` still errors).
Promote them to `"error"` when those components are reworked.

The seventh finding _was_ fixed: `Notification.tsx` called `handleClose` from an effect declared above
it — a TDZ hazard that also caused a stale-closure `exhaustive-deps` warning.

### 3. TypeScript is on 6.0.3, not 7.0.2

TypeScript 7 (the native port) is `latest`, but `@typescript-eslint/parser@8.65.0` declares
`typescript ">=4.8.4 <6.1.0"` and no typescript-eslint release supports 7 yet. Pinned `~6.0.3`
(tilde, not caret — `6.1.0` would re-break that peer). Revisit when typescript-eslint ships TS 7
support.

### 4. ESLint is on 9.39.5, not 10.8.0

`eslint-plugin-react@7.37.5` peers on `eslint ^3 … ^9.7`. Every other plugin supports 10. Forcing 10
would mean overriding that peer and risking real breakage in the plugin, so 9.39.5 is the highest
genuinely-compatible version. Alternatively drop `eslint-plugin-react` (its JSX rules largely
duplicate what TypeScript already catches) and move to 10.

### 5. 27 remaining `npm audit` advisories, all dev-only and unfixable upstream

Down from 28 (2 critical, 17 high) before the upgrade. All 27 trace to just **two** transitive
packages inside the dev toolchain's own dependency trees:

- `brace-expansion` ≤5.0.7 (high) — reached via the `minimatch` vendored inside eslint and jest
- `tar` ≤7.5.20 (moderate) — reached via semantic-release

Neither reaches the published package: `dependencies` is only `classnames`, `framer-motion` and
`tailwind-merge`.

Overriding `brace-expansion` to `^5.0.9` **was tried and reverted**: v5 changed its export shape, so
the vendored `minimatch` inside eslint threw `TypeError: expand is not a function` and the linter
stopped running entirely. Wait for eslint/jest to bump their own pins.

### 6. The `commit-msg` hook does too much

`.husky/commit-msg` runs commitlint **plus** typecheck, `lint:fix`, lint-staged and the full Jest
suite, so every commit pays the whole CI cost. Conventionally commitlint belongs in `commit-msg` and
the rest in `pre-commit` (or only in CI, which now covers all of it). Left alone — it works, and
splitting it is a workflow preference.
